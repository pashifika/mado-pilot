# MadoPilot v0.2.1

MadoPilot v0.2.1 adds native window/display capture, explicit input submission,
and bounded engine-scoped diagnostics to the deterministic replay, mapping,
asset, and template-matching baseline. The native workflow is available through
the Rust facade, additive C ABI 1.2 table, and header-only C++ wrapper.

The permanent `v0.2.1` tag is the canonical source identity when this release is
published. GitHub supplies source archives for that tag. No prebuilt library,
installer, package-manager formula, or registry package is included.

## Native workflow

On a supported native host, callers can:

1. discover displays and windows and retain their stable target identities;
2. inspect non-prompting capture and input capability/permission state;
3. open a maintained capture stream with finite latest-wins buffering;
4. acquire and retain immutable frames with stream, epoch, sequence, and geometry
   identity;
5. map a retained frame or use it for template matching;
6. submit a bounded pointer, keyboard, or text sequence with explicit route,
   focus, geometry, deadline, cancellation, and fallback policy;
7. inspect an immutable one-terminal receipt containing route attempts,
   submission evidence, partial-native-effect, and bounded cleanup state;
8. correlate that input with an independently acquired strictly newer frame and
   search without treating receipt completion as visual success;
9. optionally drain finite engine-scoped diagnostic batches with exact loss
   counts and no sensitive payloads; and
10. close sessions and engines idempotently without invalidating retained public
   frames, mappings, receipts, readers, or diagnostic batches.

The Windows adapter uses Windows Graphics Capture and D3D11. It exposes
`System` pointer/keyboard/text and exact-window `WindowMessage` as separate
caller-selected routes. Retained ordinary top-level windows report
`WindowMessage` as unknown-but-attemptable with target-queue-admission evidence;
the exact repository fixture reports supported compatibility with
target-protocol acknowledgement. Neither receipt claims application consumption,
and system input is never silently substituted. Focus, integrity/UIPI, geometry
change, target loss, queue pressure, partial effect, and bounded cleanup remain
observable outcomes.

The macOS adapter uses ScreenCaptureKit, the `CGEvent` system route, and an
explicit process-scoped `ProcessDirected` route. Screen Recording and event-post
access are reported separately and never requested by the library. The
`InputControl` contract name maps to the public non-prompting event-post
preflight, not to the legacy Accessibility trust result, even when macOS groups
the grant under an Accessibility-labelled settings pane. Input rereads
post-event authority and live target authority before each irreversible event.
`System` requires focus. `ProcessDirected` imposes no focus requirement by
default but honors caller-selected `RequireFocused` without activating; it
preserves foreground and the physical cursor, addresses the retained window's
owning process, and reports unknown compatibility. Additional same-process
windows may react, it is never exact-window delivery, and neither route
substitutes for the other. Receipt evidence is invocation-only on both routes,
macOS exposes no window-message route, and each process-directed
operation/coordinate pair is advertised only after its revision-bound native
qualification rows pass on the approved Apple Silicon host.

The original deterministic replay workflow remains available on both release
targets through Rust, C, and C++.

## Public surfaces and compatibility

- The product and Cargo package version is `0.2.1`.
- Public Rust names are reviewed but remain pre-1.0. Renaming or removing a
  reviewed public item requires a superseding ADR and a Cargo-semantic version
  bump.
- C ABI 1.0 remains the permanent released prefix. ABI 1.2 replaces the
  unreleased 1.1 development draft with route capability, input submission,
  immutable receipt/attempt handles, operation activity tags, and bounded
  diagnostic readers/batches without moving or reinterpreting an ABI 1.0 value,
  structure prefix, field, or table entry.
- ABI callers must negotiate with the structure size they compiled against and
  check the returned ABI version and table extent before reading an additive
  suffix. The frozen 1.0 header remains supported. Minimum minor 1 is explicitly
  rejected; its fixture is migration and rejection evidence, not a compatibility
  promise.
- The C++ wrapper declares no binary ABI of its own. Its native RAII types call
  only the released ABI 1.2 C table and preserve C ownership and operation rules.
- Asset manifest versions remain independent of the product and C ABI versions.

## Supported and qualified systems

The source builds and is tested natively for `x86_64-pc-windows-msvc` and
`aarch64-apple-darwin`.

The qualified macOS implementation and deployment floor is Apple Silicon macOS
26.5.2 build 25F84 with SDK 26.5. Earlier macOS versions are unsupported. The
final artifact records that deployment minimum and resolves ScreenCaptureKit
through a controlled, availability-checked load path.

The qualified Windows implementation and deployment floor is Windows 11 25H2
build family 26200 on a currently serviced x64 desktop installation; the
retained boundary run used Pro build 26200.9168. Windows SDK 10.0.26100.0 is a
build input, not the runtime floor. Final-source and hosted checks are bound to
the exact exit candidate. Hosted Windows Server CI is build and contract
evidence, not an interactive desktop claim.

## Development prerequisites

The source selects Rust 1.97.1 through `rust-toolchain.toml` and uses the
committed root `Cargo.lock`.

Building the workspace requires a host-provided OpenCV 4 development installation
and a loadable libclang because the OpenCV adapter generates bindings at build
time:

- macOS: install Homebrew `opencv@4`; Xcode Command Line Tools provide libclang
  and are sufficient for the Objective-C shim;
- Windows: extract the official OpenCV 4.14.0 prebuilt release, install LLVM
  22.1.8, and configure the documented restricted discovery variables.

Screen capture and successful input also require an interactive desktop and the
operating-system permissions described above. Receipt completion proves only the
route's documented submission threshold; a caller separately evaluates visual
state when that is its success condition. These are development-tree
prerequisites, not bundled deployment dependencies. Exact installation,
discovery, licenses, and failure behavior are documented in
[third-party dependencies](https://github.com/pashifika/mado-pilot/blob/v0.2.1/docs/third-party-dependencies.md).

## Distribution scope

This release intentionally does not provide:

- crates.io packages; every workspace crate remains `publish = false`;
- prebuilt Windows or macOS libraries;
- ABI-major decorated release-library names;
- a CMake install/export set or pkg-config metadata;
- static libraries;
- bundled OpenCV, ONNX Runtime, or another native dependency; or
- an installer or package-manager integration.

The C and C++ examples consume the development tree through the included CMake
targets. Reserved packaging names remain future contracts and do not identify
files shipped by v0.2.1.

## Known limitations

MadoPilot v0.2.1 remains a developer-facing source runtime. It does not:

- perform OCR;
- expose visual-condition watchers or their queues/scheduling;
- infer application consumption or visual success from an input receipt;
- provide GPU matching or another acceleration backend;
- publish installable native artifacts; or
- provide a GUI, tray, overlay, editor, updater, workflow catalog, general
  scripting DSL, or time-based scheduler.

Hosted CI cannot establish an interactive permission, focus, input, display,
GPU/device, target-loss, or minimum-system claim. Revision-bound native
acceptance therefore comes from the approved physical hosts: all fourteen
macOS controlled owning-process pairs, macOS production capture/transitions,
the Windows 11 25H2 minimum boundary, Windows 1280×720 production
capture/transitions, and corrected Windows mixed-DPI dual-4K production capture
passed their independent source, topology, correctness, and budget gates.
Physical Windows device removal, TDR, and driver upgrade were not performed and
are not claimed; injected device loss verifies the state machine only.
Exact-candidate Phase 1 and repository checks do not widen those physical claims.

The `ProcessDirected` contract remains owning-process, unknown-compatibility,
and invocation-only. Minimized-window automation, exact-window delivery inside
a multi-window process, arbitrary application or game compatibility, and
real-time input latency are out of scope. AppKit terminal p95 was
`56.466375 ms` under the frozen `106.34 ms` ceiling; controlled OpenGL
game-like p95 was `56.699333 ms` under `112.18 ms`. Both profiles recorded
zero correctness failures, one matching fixture event per terminal sequence,
unchanged foreground and physical cursor, and zero post-warm-up allocation
growth. Those values never apply to `RequireFocused`, `ReprojectCurrent`,
fallback, another renderer or input stack, or application consumption. The
ADR 0030 separately accepts the macOS production-capture and transition
profiles, ADR 0031 accepts the Windows 1280×720 production-capture and
transition profiles, and ADR 0032 accepts corrected Windows mixed-DPI dual-4K
production capture. Exact-candidate checks remain separate release evidence.

## Security and privacy

MadoPilot performs no implicit network access, privilege escalation, or permission
request. Native target selection is explicit; public examples reject absent or
ambiguous exact-title matches. Cancellation and deadlines are checked before
irreversible input and result commit, and sequence cleanup releases only state
pressed by that sequence under a shared bound.

Ordinary logs, diagnostic records, and retained evidence exclude captured images,
pixel hashes, recognized or injected text, credentials, process paths, unrelated
window titles, platform namespaces, backend names, signing identifiers, native
free-form messages, and other desktop payload by default. Native fixtures retain
bounded event-kind and unit counts, never input text. Asset loading remains
network-free and rejects absolute paths, traversal, links, special files,
duplicate normalized entries, hash mismatches, and archive resource-limit
violations.

The host remains responsible for permissions and for the legality of the
automation it builds.

## Upgrading from v0.1.0

C consumers compiled against ABI 1.0 continue to negotiate and run against the
1.2 library without source changes. Consumers built against the unreleased 1.1
draft must recompile against the 1.2 header and request minimum minor 2. There is
no minor-1 compatibility promise, alias, or shim.

For those draft callers:

- replace the removed `BackgroundTarget` delivery value with an explicit choice:
  `WindowMessage` means exact-window, focus-preserving queue submission on
  Windows; `ProcessDirected` means owning-process-scoped, foreground-preserving
  posting on macOS with unknown compatibility; `System` means operating-system
  input and its documented focus policy;
- query each operation/route pair and its support, address scope, and evidence
  ceiling. Ordinary Windows `WindowMessage` is intentionally `Unknown`, not
  `Supported`; permitting an unknown-but-attemptable route is a caller policy
  decision;
- replace direct `delivered`/`last_completed` fields with the immutable receipt's
  `submitted` count, optional last-submitted index, outcome, evidence, typed
  fault, attempt list, and cleanup state; and
- treat receipt completion as a submission fact. If application effect matters,
  acquire and evaluate a strictly newer frame as a separate operation.

C++ callers make the same migration through the ABI 1.2 native wrapper types.
Owned receipt and attempt values replace the unreleased borrowed draft shape;
the deterministic replay wrapper flow is unchanged.

Rust callers update the source dependency to `0.2.1`. Existing deterministic
calls remain available. Native behavior is additive and stays behind explicit
target, capability, permission, route, focus, geometry, deadline, and
cancellation objects. `InputDelivery::WindowMessage` is never an implicit
fallback to `InputDelivery::System`, and a route cannot advance after native
submission may have had an effect.
