# MadoPilot v0.3.0 candidate

MadoPilot v0.3.0 integrates the accepted G-004 Japanese/basic-Latin CPU OCR profile as an explicit production default through Rust, C ABI 1.3, and the header-only C++ wrapper. It preserves caller-supplied OCR backends and schema-v2 asset packages; the default is a separate constructor, not an ambient fallback.

This file is the canonical candidate release body. v0.3.0 is not published or supported yet. The approved Windows 11 integrated 42-region quality rerun and numeric OCR performance profile are missing, so no tag, support-table promotion, or release artifact is justified by hosted CI alone.

## Integrated default OCR

The default profile identity is `g-004-rapidocr-ppocrv4-det-v6-rec-small-v1`:

- RapidOCR v3.9.2 `ch_PP-OCRv4_det_mobile.onnx`, 4,745,517 bytes, SHA-256 `d2a7720d45a54257208b1e13e36a8479894cb74155a5efe29462512d42f49da9`;
- RapidOCR v3.9.2 `PP-OCRv6_rec_small.onnx`, 21,234,383 bytes, SHA-256 `6f327246b50388f3c176ae304bd95767ea6dc0c9ae92153ef8cbe210b3c14884`;
- 18,708-entry vocabulary, SHA-256 `f7aa897ca828a4c7c9e2739c30f9161a33306d532f020bcdb91dcfb664a5507e`; and
- ONNX Runtime 1.29.0, C API 17, CPU provider only.

Rust callers use `DefaultOcrConfig` with `replay_engine_with_default_ocr`, `windows_engine_with_default_ocr`, or `macos_engine_with_default_ocr`. C callers negotiate through `MADOPILOT_API_SIZE_ENGINE_CREATE_WITH_DEFAULT_OCR` and call `engine_create_with_default_ocr`. C++ callers use `DefaultOcrOptions` and `Api::create_engine_with_default_ocr`. The production examples are:

```text
crates/mado-pilot/examples/ocr-default.rs
crates/bindings/capi/examples/c/ocr-default.c
crates/bindings/capi/examples/cpp/ocr-default.cpp
```

The default path reads only these fixed model-root-relative files:

```text
rapidocr-v3.9.2/ch_PP-OCRv4_det_mobile.onnx
rapidocr-v3.9.2/PP-OCRv6_rec_small.onnx
```

The caller also supplies one canonical absolute runtime path: `libonnxruntime.1.29.0.dylib` on Apple Silicon or `onnxruntime.dll` on Windows. MadoPilot does not bundle, install, download, search `PATH`, use an environment override internally, select another provider, or retry with another model. The runtime remains loaded for process life because the process-global API table contains pointers into it.

The two model files are Apache-2.0 material and ONNX Runtime is MIT. They remain controlled host-provided prerequisites, not v0.3.0 artifacts. OpenCV 4 remains a separate host-provided development-tree prerequisite.

## Public surfaces and compatibility

- The workspace and Cargo package version is `0.3.0`.
- Existing constructors still omit OCR unless a caller supplies an explicit backend. The new `*_engine_with_default_ocr` constructors fail construction on a missing, non-canonical, wrong-name, wrong-version, wrong-length, or wrong-digest prerequisite; they never return a half-configured engine.
- Explicit schema-v2 asset-package OCR remains available. Default composition reads the accepted fixed paths directly and does not create a duplicate 25,979,900-byte package allocation.
- Every request still names the exact retained frame, backend/model identity, region, output coordinate space, operation deadline, and cancellation state. OCR does not trigger input.
- C ABI 1.0 and 1.2 remain permanent complete 424-byte and 592-byte prefixes. ABI 1.3's original OCR owner/accessor suffix ends at 640 bytes; `engine_create_with_default_ocr` extends the complete ABI 1.3 table to 648 bytes without moving a prior entry.
- A C default request may set `package = NULL` only when its backend/model views name the exact default identities reported by `describe_build`. Explicit package-backed models continue to require their package owner for the synchronous call.
- C++ owners remain move-only with explicit `clone()`. `DefaultOcrOptions` owns its path strings; `OcrRequest` borrows its frame and borrows a package only when one is set.

The unreleased ABI 1.1 draft remains unsupported. Recompile against ABI 1.2 or 1.3; do not copy draft numeric values or layouts.

## Quality and performance status

The accepted profile's original cross-target G-004 selection evidence remains bound to ADR 0033 and its recorded candidate revisions. On the integrated candidate, the approved Apple Silicon host reran the same predeclared 42-region matrix: the accepted hybrid passed all regions, and all three rejected candidates reproduced their historical rejection categories. The matching approved Windows 11 integrated rerun is still missing.

ADR 0037 accepts only the Apple M1 Pro OCR regression profile. Five fresh precursor processes retained 50 correct samples per workload with zero allocation growth. The final post-budget process passed every executable ceiling:

| Workload | Observed p95 | Ceiling | Mapped/copied bytes |
|---|---:|---:|---:|
| 960×540 full HUD | 469.992 ms | 750 ms | 2,073,600 / 0 |
| 180×90 bounded region | 306.045 ms | 450 ms | 64,800 / 0 |
| 64×64 empty result | 133.130 ms | 210 ms | 16,384 / 0 |

Cold default open was 84.629 ms under 140 ms; first close 1.007 ms under 2 ms; reopen plus close 62.536 ms under 100 ms; maximum resident set 544,391,168 bytes under 768 MiB. These are target-specific regression gates, not arbitrary-resolution, 4K, multi-region, real-time, Windows, renderer, application, or game-compatibility guarantees. No Windows numeric ceiling is inferred from Apple or hosted Windows Server.

## Running the development-tree examples

Set the two environment variables only to pass reviewed paths into an example; the library itself performs no environment lookup:

```sh
export MADO_PILOT_G004_MODEL_ROOT=/canonical/model/root
export MADO_PILOT_ONNX_RUNTIME=/canonical/path/libonnxruntime.1.29.0.dylib
cargo run --locked --package mado-pilot --example ocr-default
cargo build --locked --package mado-pilot-capi
cargo run --locked --package mado-pilot-capi --example c-abi-check -- --label "<host>"
```

On Windows, use a canonical absolute path to `onnxruntime.dll`. The C ABI checker compiles and runs the production C and C++ default examples, compares their normalized output, and then runs the independent CMake consumer.

## Troubleshooting

- `controlled ONNX runtime is unavailable`: the runtime path is missing, non-canonical, the wrong target filename, or cannot be loaded with the restricted target flags.
- `controlled ONNX runtime is incompatible`: the file did not report exact version `1.29.0` and API 17.
- `OCR model source is invalid`: a fixed model file is missing, not a regular file, has the wrong length/digest, or its graph/vocabulary metadata does not match the accepted profile.
- `OCR backend is busy`: the profile admits one synchronous inference; it does not queue or run the session concurrently.
- `operation was cancelled` or `operation deadline passed`: no late result is published. A cancellation after native admission issues bounded best-effort termination and the backend remains reusable.
- macOS Screen Recording and event-post access remain separate non-prompting native capabilities. OCR over replay frames requires neither and never requests a permission.

Errors and diagnostics do not include model/runtime paths, model bytes/digests, pixels or hashes, recognized text, credentials, native identifiers, process inventories, or unrelated desktop metadata. OCR diagnostics carry only bounded source/request geometry, timing/count, opaque model-instance correlation, accepted-profile classification, and typed outcome.

## Distribution scope and known limitations

This candidate remains a developer-facing source runtime. It publishes no crates.io packages, prebuilt libraries, installer, package-manager formula, CMake install/export set, pkg-config file, static library, ABI-major decorated loader artifact, OpenCV, ONNX Runtime, or model file.

It does not provide visual-condition watchers, wait-for-text, OCR scheduling/coalescing, callbacks, retries, automatic input, multi-region request batching, internal arbitrary-frame downscaling, GPU/provider fallback, packaging downloads, a GUI, tray, overlay, editor, updater, workflow catalog, general scripting DSL, or time-based scheduler.

The release remains blocked until the exact integrated candidate has approved Windows 11 25H2 42-region quality and numeric performance evidence, all final repository/native/public-language gates pass, independent review is clean, and the protected release flow produces the permanent tag. Hosted Windows Server correctness smoke is useful evidence but not a substitute.
