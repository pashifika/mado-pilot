# MadoPilot v0.2.0

MadoPilot v0.2.0 adds native window/display capture and explicit input delivery to
the deterministic replay, mapping, asset, and template-matching baseline. The
native workflow is available through the Rust facade, the additive C ABI 1.1
table, and the header-only C++ wrapper.

The permanent `v0.2.0` tag is the canonical source identity when this release is
published. GitHub supplies source archives for that tag. No prebuilt library,
installer, package-manager formula, or registry package is included.

## Native workflow

On a supported native host, callers can:

1. discover displays and windows and retain their stable target identities;
2. inspect non-prompting capture and input capability/permission state;
3. open a maintained capture stream with finite latest-wins buffering;
4. acquire and retain immutable frames with stream, epoch, sequence, and geometry
   identity;
5. map a retained frame or use it for template matching;
6. submit a bounded pointer, keyboard, or text sequence with explicit delivery,
   focus, geometry, deadline, cancellation, and fallback policy;
7. inspect a one-terminal receipt, including partial delivery and bounded cleanup;
   and
8. close sessions and engines idempotently without invalidating retained public
   frames or mappings.

The Windows adapter uses Windows Graphics Capture and D3D11. It exposes system
pointer/keyboard/text delivery and fixture-class background pointer/keyboard
mechanisms as separate capabilities; it never silently substitutes system input
for a refused background request. Focus, integrity/UIPI, geometry change, target
loss, and device reset/removal remain observable outcomes.

The macOS adapter uses ScreenCaptureKit and `CGEvent` system delivery. Screen
Recording and Accessibility are reported separately and are never requested by
the library. Input rereads Accessibility and live target geometry before each
irreversible event. macOS exposes no background input mechanism.

The original deterministic replay workflow remains available on both release
targets through Rust, C, and C++.

## Public surfaces and compatibility

- The product and Cargo package version is `0.2.0`.
- Public Rust names are reviewed but remain pre-1.0. Renaming or removing a
  reviewed public item requires a superseding ADR and a Cargo-semantic version
  bump.
- C ABI 1.0 remains the permanent prefix. ABI 1.1 appends engine capability,
  permission, native session, and bounded input entries without moving or
  reinterpreting an ABI 1.0 value, structure prefix, field, or table entry.
- ABI callers must negotiate with the structure size they compiled against and
  check the returned ABI version and table extent before reading an additive
  suffix. The frozen 1.0 and 1.1 headers remain supported.
- The C++ wrapper declares no binary ABI of its own. Its new native RAII types
  call only the released ABI 1.1 C table and preserve the C ownership and
  callback-fence rules.
- Asset manifest versions remain independent of the product and C ABI versions.

See the
[architecture baseline](https://github.com/pashifika/mado-pilot/blob/v0.2.0/docs/architecture.md),
[C ABI contract](https://github.com/pashifika/mado-pilot/blob/v0.2.0/docs/c-abi.md),
and
[C++ wrapper contract](https://github.com/pashifika/mado-pilot/blob/v0.2.0/docs/cpp-wrapper.md)
for the complete contracts.

## Supported and qualified systems

The source builds and is tested natively for `x86_64-pc-windows-msvc` and
`aarch64-apple-darwin`.

The qualified macOS implementation and deployment floor is Apple Silicon macOS
26.5.2 build 25F84 with SDK 26.5. Earlier macOS versions are unsupported. The
final artifact records that deployment minimum and resolves ScreenCaptureKit
through a controlled, availability-checked load path.

The proposed Windows boundary is Windows 11 25H2 with SDK 10.0.26100.0 as a build
input. This release must not be published until the approved Windows desktop has
run the boundary and interactive matrices and the resulting ADR records the
exact supported minimum. Hosted Windows Server CI is build and contract evidence,
not an interactive desktop or minimum-system claim.

## Development prerequisites

The source selects Rust 1.97.1 through `rust-toolchain.toml` and uses the
committed root `Cargo.lock`.

Building the workspace requires a host-provided OpenCV 4 development installation
and a loadable libclang because the OpenCV adapter generates bindings at build
time:

- macOS: install Homebrew `opencv@4`; Xcode Command Line Tools provide libclang
  and are sufficient for the Objective-C shim;
- Windows: extract the official OpenCV 4.14.0 prebuilt release, install LLVM
  22.1.8, and configure the documented restricted discovery variables.

Screen capture and successful input also require an interactive desktop and the
operating-system permissions described above. These are development-tree
prerequisites, not bundled deployment dependencies. Exact installation,
discovery, licenses, and failure behavior are documented in
[third-party dependencies](https://github.com/pashifika/mado-pilot/blob/v0.2.0/docs/third-party-dependencies.md).

## Distribution scope

This release intentionally does not provide:

- crates.io packages; every workspace crate remains `publish = false`;
- prebuilt Windows or macOS libraries;
- ABI-major decorated release-library names;
- a CMake install/export set or pkg-config metadata;
- static libraries;
- bundled OpenCV, ONNX Runtime, or another native dependency; or
- an installer or package-manager integration.

The C and C++ examples consume the development tree through the included CMake
targets. Reserved packaging names remain future contracts and do not identify
files shipped by v0.2.0.

## Known limitations

MadoPilot v0.2.0 remains a developer-facing source runtime. It does not:

- perform OCR;
- expose visual-condition watchers or their queue/scheduling diagnostics;
- provide GPU matching or another acceleration backend;
- publish installable native artifacts; or
- provide a GUI, tray, overlay, editor, updater, workflow catalog, general
  scripting DSL, or time-based scheduler.

A one-display macOS matrix cannot establish shared-display signed-origin or
cross-scale behavior. Hosted CI cannot establish an interactive permission,
focus, input, display, GPU/device, target-loss, or minimum-system claim. The
release remains blocked while the macOS shared external-display matrix and the
Windows single-display and shared mixed-DPI matrices are unavailable.

## Security and privacy

MadoPilot performs no implicit network access, privilege escalation, or permission
request. Native target selection is explicit; the public examples reject absent
or ambiguous exact-title matches. Cancellation and deadlines are checked before
irreversible input and result commit, and sequence cleanup releases only state
pressed by that sequence under a shared bound.

Ordinary logs and retained evidence exclude captured images, pixel hashes,
recognized or injected text, credentials, process paths, unrelated window titles,
and other desktop payload by default. Native fixtures retain bounded event-kind
and unit counts, never input text. Asset loading remains network-free and rejects
absolute paths, traversal, links, special files, duplicate normalized entries,
hash mismatches, and archive resource-limit violations.

The host remains responsible for permissions and for the legality of the
automation it builds.

## Verification evidence

The release candidate carries:

- repository inventory and dependency-direction enforcement;
- formatting, clippy, workspace tests, doctests, rustdoc, dependency-policy, and
  native Rust/C/C++ checks in hosted CI;
- frozen ABI 1.0 and 1.1 header compatibility, layout, invalid-input, panic and
  exception containment, ownership, callback-fence, and concurrent-close checks;
- deterministic replay regressions on both release targets;
- a revision-bound Apple Silicon current-display matrix with all 160 macOS
  library cases under AddressSanitizer, exact owned-window replacement, and Rust,
  C, and C++ native input flows; and
- Phase 1 budgets plus accepted Phase 2 macOS capture, lifecycle, input, and
  process-load budgets with hard correctness and bounded-growth predicates.

The evidence explicitly records the unavailable Windows performance and
interactive matrices, the unavailable macOS shared-display matrix, and the two
unbudgeted C/C++ common-flow resident-memory workloads. Those gaps are not passes
and must be closed before publication.

## Upgrading from v0.1.0

C consumers compiled against ABI 1.0 continue to negotiate and run against the
1.1 library without source changes. Consumers that opt into native capabilities
must compile against the 1.1 header, pass the caller-known table extent, and use
the new owned handles and release functions. C++ consumers likewise opt into the
new native wrapper types without changing the deterministic wrapper flow.

Rust consumers update the source dependency to `0.2.0`. Existing deterministic
calls remain available; native behavior is additive and stays behind explicit
target, capability, permission, request-policy, deadline, and cancellation
objects.
